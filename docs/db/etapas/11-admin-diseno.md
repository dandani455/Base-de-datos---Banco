## 3. Diseño

**Orden común de todas las públicas** (como E5–E10): `_validar_admin(p_admin_id)` **primero y antes de leer nada** (`Acceso denegado` si no existe o no es ADMIN; el mensaje de bloqueo si el admin está bloqueado: se relee en cada petición) → validar parámetros → (si lee o escribe saldos) `_reloj_instantanea()` UNA vez + `_avanzar_hasta` + bloqueo de la cuenta → acción → auditoría → respuesta. Todas `SECURITY DEFINER`, `search_path = public, pg_temp`, `SET TimeZone = 'America/Bogota'` donde emiten fechas (D-E10-8). **`p_admin_id uuid` es SIEMPRE el primer parámetro** (el backend lo pone desde la sesión):

Las 3 de tasas (10–12): `p_tasa` llega como **texto** tal cual lo manda el front (`"12.5"`), se valida con `_parse_tasa` (`0 < tasa ≤ 100`, hasta 3 decimales; si no, `Tasa inválida` — nunca un error de driver 22P02, porque un texto no numérico caería en el 400 genérico del backend), el id inexistente o mal formado es `Recurso no encontrado` (el mock lo ignoraba en silencio), y toman un **`pg_advisory_xact_lock` común** al empezar: dos administradores que guardan a la vez **se serializan por transacción completa** (no hay deadlock por orden de filas y el estado final es el de **uno** de los dos formularios, completo). **No tocan nada ya creado** (las tasas están copiadas). Cada una escribe su evento `TASA_CAMBIO` (entidad, antes/después); con la transacción del backend, o todos o ninguno.

**Internas** (sin EXECUTE para nadie salvo el dueño): `_reglas_admin()` (valores provisionales en un solo lugar: tope 200 de la lista, nota 140, 3 decimales de tasa), `_parse_tasa(texto, permite_cero)` (única validación de tasas y del 0 ↔ NULL de la mora), `_cliente_objetivo(texto, por_referencia)` (uuid o, para el ajuste, username/cuenta → el CLIENTE o `Recurso no encontrado`, sin distinguir ajeno/inexistente/ADMIN), `_auditar_admin(admin, accion, entidad, entidad_id, antes, despues)` (único escritor de eventos admin; también hace `set_config('banco.actor', username, true)`).

**Permisos.** Las 12 públicas: `EXECUTE` solo para `banco_app` (`banco_dev` hereda); las 4 internas: nadie. **El control de acceso es la función, no el rol de conexión:** `banco_app` ejecuta también las de cliente, así que un cliente con sesión válida **no** puede usar `admin_*` porque `_validar_admin` lo rechaza (se prueba con las 12, una a una; el backend añade además `requireAdmin`). Ninguna escritura directa de tablas para `banco_app`. Esperado: **109 → 125 funciones**, lista blanca de `banco_app` **26 → 38**, vistas 9, triggers 21 (**ninguno nuevo**), tablas sin cambios.

## 4. Integración, concurrencia e integridad

* **Con el motor (E7–E9):** `admin_detalle_usuario` y `admin_ajustar_balance` «devengan» (catálogo de `54`: 17 → 19); las otras **10** son **exentas**. Cada una llama `_reloj_instantanea()` y `_avanzar_hasta(` **una sola vez**, instantánea primero. Consecuencia a documentar: *consultar* a un usuario como admin puede **cobrarle una cuota con descuento automático o cerrar su CDT** (la semántica perezosa de todo el banco).
* **Con el libro (E2):** el dinero solo por `_asentar_grupo`; el ajuste respeta cuadre, tope `monto_maximo` y saldo ≥ 0. El borrado destruye saldos y deuda **a la vista**: `CUENTA_BORRADA` los guarda y `v_integridad_global` los concilia (`transf_neto_borrados`).
* **Con el reloj (E3):** `admin_set_reloj` toma el mismo `UPDATE` de E3; las operaciones en vuelo terminan antes; dos admins se serializan.
* **Con E4–E10:** un cliente **bloqueado** pierde acceso en su siguiente petición; uno **borrado** en plena operación recibe `Sesión inválida`. Recibir dinero estando bloqueado sigue siendo **sí** (D-E5-9, equipo).
* **Bloqueos:** el borrado y el ajuste toman el bloqueo de la cuenta objetivo (el del libro) → sin ciclos nuevos; las tasas se serializan con el advisory lock; `admin_bloquear` es un `UPDATE` de una fila.
* **Atomicidad:** cada función es una transacción (acción + evento); si algo falla no queda **nada**. La atomicidad del formulario de tasas completo la da la transacción del backend (§2, §9).
* **Los eventos admin no son un control de seguridad** (atribución, como `banco.actor` en E2/E3). Un superusuario puede saltarse las funciones (límite honesto ya documentado).

## 8. Riesgos y límites

1. **Consultar a un usuario como admin puede cobrarle** (motor perezoso); coherente con el resto del banco.
2. **Borrar destruye dinero y deuda** (spec §15.5): queda trazado en `audit.evento`; no es reversible.
3. **Cambiar la mora recalcula la mora vencida** (derivada, E9): **sin confirmar por el equipo** (D-E11-D7b).
4. **La atomicidad del formulario de tasas depende de que el backend use una transacción** (hoy `db.tx`, verificado). Si alguien llamara las 3 funciones por separado, cada una sería atómica pero no el conjunto (alternativa B de D-E11-7).
5. **`admin_*` y las funciones de cliente comparten el rol `banco_app`:** la separación depende de `_validar_admin` (probado en las 12 y vigilado por el escaneo de catálogo) y de `requireAdmin` del backend.
6. **Sin ADMIN en la BD recién aplicada** (el primero lo crea el seed, E14, D5): E11 se prueba con admins de prueba; `admin_*` no crea administradores.
7. **El front no muestra el UUID del usuario:** el ajuste se apoya en username/cuenta.
8. **El backend de `origin/main` fue escrito contra las firmas del plan, no contra las de E4–E10** (§9): requiere una revisión de integración que **no es de E11**.

> **Aviso (2026-11-25):** el backend de `origin/main` es un borrador temporal y **no es fuente de autoridad** para E11 ni las etapas siguientes; esta sección documenta lo que se observó entonces. El parche asociado es solo referencia descartable y no está integrado (ver `11-admin.md` §8).
